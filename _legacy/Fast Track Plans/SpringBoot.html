01. Introduction & Node.js $\to$ Spring Boot Mental Model

1.1 The Runtime Shift: V8 Single-Threaded Event Loop vs. JVM & Virtual Threads (Loom)

In Node.js, your JavaScript code executes on a single thread powered by the V8 engine and the libuv event loop. Asynchronous operations (disk reads, database queries, outbound network requests) are offloaded to OS kernel polling (epoll/kqueue) or the libuv worker threadpool (default 4 threads). Once an I/O task finishes, its callback or promise is pushed to an event queue and placed onto the call stack when the thread is idle:

[ Node.js Request ] ──> Event Loop (Single Thread) ──> Offload I/O ──> Event Queue ──> Callback/Promise

In classic Java (Spring Boot 1.x & 2.x), the server model was thread-per-request backed by OS-level kernel threads managed by an embedded Apache Tomcat pool (default 200 threads). If 200 concurrent requests each performed a 500ms database query, all 200 OS threads were strictly blocked waiting for network packets. Because an OS thread carries a heavy memory footprint (~1MB stack size) and incurs high CPU context-switching overhead, scaling to 10,000+ concurrent requests required complex reactive programming (Spring WebFlux / Project Reactor), which introduced callback complexity similar to early Node.js callback hell.

In modern Spring Boot 3 + Java 21, the game changed fundamentally with Project Loom (Virtual Threads). Virtual threads are lightweight user-mode threads managed entirely by the JVM rather than the OS kernel. You can create millions of virtual threads concurrently with negligible memory overhead (~few hundred bytes).

When a virtual thread executes a blocking operation (e.g., standard JDBC query, blocking HTTP request, file read), the JVM automatically unmounts the virtual thread from its underlying OS carrier thread. The carrier thread immediately proceeds to run other virtual threads. When the I/O completes, the JVM unblocks and remounts the virtual thread on an available carrier thread:

Concurrency Architecture Shift
💡 Production Takeaway for Node Developers: You no longer have to write non-blocking reactive chains (`Mono`, `Flux`, or nested promises) in Java. Write clean, readable, sequential synchronous code—the JVM manages the high-throughput asynchronous execution underneath via Virtual Threads.

1.3 Inversion of Control (IoC) & Dependency Injection (DI) Under the Hood

In standard Node.js, you instantiate classes manually or import singleton instances from files:

Node.js / TypeScript Singleton
// Node.js
import { db } from "./db";
export class ProductService {
  async getProducts() { return db.query("SELECT * FROM products"); }
}
export const productService = new ProductService(); // Exported singleton

In Spring Boot, you never use new ProductService(). The Spring IoC Container manages the full lifecycle of your application components (called Beans). When the application boots, Spring scans your packages for annotations (`@Component`, `@Service`, `@Repository`, `@RestController`), instantiates single instances, resolves their dependencies, and wires them together via Constructor Injection:

ProductService.java (Constructor Injection) 
@Service
public class ProductService {

    private final ProductRepository productRepository;

    // Spring automatically supplies the ProductRepository bean at runtime
    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }
}
⚠️ Enterprise Rule: Avoid Field Injection (`@Autowired private ProductRepository repo;`) Field injection makes unit testing difficult because dependencies cannot be provided without launching the entire Spring container. Constructor injection guarantees immutability via final fields and allows pure unit tests by instantiating the class with mock dependencies.

1.4 Annotations Demystified: Dynamic Proxies & Bytecode Instrumentation

To JavaScript developers, Spring annotations (`@Transactional`, `@Cacheable`, `@PreAuthorize`) look like magic. Under the hood, Spring uses CGLIB Dynamic Proxies and Aspect-Oriented Programming (AOP).

When you annotate a class or method with @Transactional, Spring generates an intermediate proxy subclass wrapping your bean. When a client calls your method, it hits the proxy first:

Dynamic Proxy & Transaction Interceptor
Client Call ➔ CGLIB Proxy (Intercepts call) ➔ BEGIN TX ➔ Real Service Execution ➔ COMMIT / ROLLBACK

04. REST APIs, DTOs & Jakarta Validation

4.1 Immutable DTOs using Java Records

In modern Java, Records replace bulky boilerplate classes. A record provides an immutable data carrier with automatically generated constructor, getters (`name()`), `equals()`, `hashCode()`, and `toString()`:

ProductDTOs.java (Jakarta Validation Annotations) 
package com.ecommerce.product.dto;

import jakarta.validation.constraints.DecimalMin;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import java.math.BigDecimal;

public class ProductDTOs {

    // Request DTO with validation constraints (zod equivalent)
    public record CreateProductRequest(
        @NotBlank(message = "Product name cannot be blank")
        String name,

        String description,

        @NotNull(message = "Price is required")
        @DecimalMin(value = "0.01", message = "Price must be greater than zero")
        BigDecimal price,

        @NotBlank(message = "SKU code is required")
        String skuCode
    ) {}

    // Response DTO
    public record ProductResponse(
        Long id,
        String name,
        String description,
        BigDecimal price,
        String skuCode
    ) {}
}

4.2 REST Controller Implementation

Controllers map HTTP verbs to Java methods, deserialize payloads, trigger validations, and return HTTP status codes:

ProductController.java 
package com.ecommerce.product.controller;

import com.ecommerce.product.dto.ProductDTOs.*;
import com.ecommerce.product.service.ProductService;
import jakarta.validation.Valid;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;
import java.util.List;

@RestController
@RequestMapping("/api/v1/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @PostMapping
    public ResponseEntity<ProductResponse> createProduct(
            @Valid @RequestBody CreateProductRequest request
    ) {
        ProductResponse response = productService.createProduct(request);
        return ResponseEntity
                .created(URI.create("/api/v1/products/" + response.id()))
                .body(response);
    }

    @GetMapping
    public ResponseEntity<List<ProductResponse>> getAllProducts() {
        return ResponseEntity.ok(productService.getAllProducts());
    }

    @GetMapping("/{id}")
    public ResponseEntity<ProductResponse> getProductById(@PathVariable Long id) {
        return ResponseEntity.ok(productService.getProductById(id));
    }
}

4.3 Global Exception Handling (RFC 7807 `ProblemDetail`)

In Express, you would write an error middleware: app.use((err, req, res, next) => ...). In Spring Boot 3, use @RestControllerAdvice emitting standardized RFC 7807 payloads:

GlobalExceptionHandler.java 
package com.ecommerce.product.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.net.URI;
import java.time.Instant;
import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ProductNotFoundException.class)
    public ProblemDetail handleProductNotFound(ProductNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Product Not Found");
        problem.setType(URI.create("https://api.ecommerce.com/errors/not-found"));
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidationExceptions(MethodArgumentNotValidException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST, "Validation failed for one or more fields"
        );
        problem.setTitle("Bad Request");

        Map<String, String> invalidFields = new HashMap<>();
        for (FieldError error : ex.getBindingResult().getFieldErrors()) {
            invalidFields.put(error.getField(), error.getDefaultMessage());
        }
        problem.setProperty("invalidParams", invalidFields);
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }
}

05. Persistence & Data Layer with Spring Data JPA & Hibernate

5.1 ORM Mental Model: Prisma vs. Hibernate

In Prisma, entities are simple JSON objects. When you query records, Prisma executes an explicit SQL query. To save changes, you must explicitly call prisma.user.update(...).

In Hibernate (JPA), entities are stateful managed objects inside an in-memory Persistence Context (First-Level Cache). When an entity is loaded within a @Transactional boundary:

  • Hibernate tracks initial property snapshots.
  • If you mutate a field (e.g., product.setPrice(newPrice)), Hibernate's Dirty Checking detects the mutation automatically.
  • When the transaction commits, Hibernate issues the SQL UPDATE statement automatically. Calling repository.save() on an already managed entity is completely redundant.

5.2 JPA Entity Definition

Product.java 
package com.ecommerce.product.entity;

import jakarta.persistence.*;
import lombok.*;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "products", indexes = {
    @Index(name = "idx_products_sku", columnList = "sku_code", unique = true)
})
@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String name;

    @Column(columnDefinition = "TEXT")
    private String description;

    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal price;

    @Column(name = "sku_code", nullable = false, unique = true, length = 50)
    private String skuCode;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @PrePersist
    protected void onCreate() {
        this.createdAt = Instant.now();
    }
}

5.3 Solving the $N+1$ Query Problem

The most infamous ORM performance bug: fetching 10 Orders executes 1 query for orders, and 10 separate queries to fetch the items for each order ($N+1$ queries).

OrderRepository.java (JOIN FETCH) 
public interface OrderRepository extends JpaRepository<Order, Long> {

    // PREVENTS N+1: JOIN FETCH loads Order and OrderItems in a SINGLE SQL INNER JOIN
    @Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.orderNumber = :orderNumber")
    Optional<Order> findByOrderNumberWithItems(@Param("orderNumber") String orderNumber);
}

5.4 Declarative Transactions: `@Transactional` Rules

By default in Spring, transactions roll back only on unchecked exceptions (`RuntimeException` and `Error`). If a checked `Exception` is thrown, the transaction commits! Always configure explicit rollback behavior:

// Rollback on ANY exception including checked exceptions
@Transactional(rollbackFor = Exception.class)
public Order processOrder(OrderRequest req) throws PaymentException { ... }

08. OpenFeign & Resilience4j Circuit Breakers

8.2 Resilience4j Circuit Breakers

If InventoryService crashes or hangs, the calling service must not exhaust its threads. A Circuit Breaker monitors failure rates and opens the circuit:

InventoryFallbackService.java 
package com.ecommerce.order.service;

import com.ecommerce.order.client.InventoryClient;
import com.ecommerce.order.client.InventoryClient.InventoryResponse;
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import java.util.Collections;
import java.util.List;

@Service
@Slf4j
public class InventoryFallbackService {

    private final InventoryClient inventoryClient;

    public InventoryFallbackService(InventoryClient inventoryClient) {
        this.inventoryClient = inventoryClient;
    }

    @CircuitBreaker(name = "inventory", fallbackMethod = "fallbackCheckStock")
    public List<InventoryResponse> checkInventoryWithResilience(List<String> skuCodes) {
        return inventoryClient.checkStock(skuCodes);
    }

    // Fallback executed when circuit is OPEN or call times out
    public List<InventoryResponse> fallbackCheckStock(List<String> skuCodes, Throwable throwable) {
        log.error("Inventory service unreachable. Reason: {}", throwable.getMessage());
        return Collections.emptyList();
    }
}

10. Distributed Transactions & The Saga Pattern

10.1 The Microservices Consistency Dilemma

In a monolith, placing an order and decrementing stock happens inside a single `@Transactional` DB transaction. In microservices:

  • OrderService writes to Orders_DB
  • InventoryService writes to Inventory_DB
  • PaymentService communicates with Stripe / Payment Gateway

If Stripe declines the card, how do you roll back the stock reservation in `InventoryService`? We use the Choreography Saga Pattern with Compensating Actions:

Saga State Transitions & Compensations
1. OrderCreated: Order saved with status PENDING.
2. StockReserved: Inventory listens, decrements inventory. Emits StockReserved.
3. PaymentAttempted: Payment service charges card.
4. If Payment Declined (Compensating Transaction): Emits PaymentFailed. Inventory listens and increments back stock (Release Reservation). Order listens and marks order as CANCELLED.

10.2 The Transactional Outbox Pattern

To eliminate dual-write bugs where the database commit succeeds but the network disconnects before publishing to Kafka, write the event into an Outbox table inside the same local database transaction:

OrderServiceOutbox.java 
@Transactional
public Order createOrder(OrderRequest request) {
    Order order = orderRepository.save(mapToEntity(request));
    
    OutboxEvent outboxEvent = OutboxEvent.builder()
            .aggregateType("ORDER")
            .aggregateId(order.getOrderNumber())
            .type("ORDER_CREATED")
            .payload(objectMapper.writeValueAsString(new OrderPlacedEvent(order)))
            .createdAt(Instant.now())
            .build();
            
    outboxRepository.save(outboxEvent); // Written atomically in PostgreSQL
    return order;
    // Debezium CDC or background job tails outbox table and streams to Kafka
}

11.2 Distributed Locking with Redisson (Preventing Overselling)

In high-concurrency flash sales, multiple instances of `InventoryService` might attempt to sell the last unit of stock simultaneously. Standard database locks can cause lock contention; use a distributed Redis lock:

ConcurrencySafeInventoryService.java (Redisson Lock) 
package com.ecommerce.inventory.service;

import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.stereotype.Service;
import java.util.concurrent.TimeUnit;

@Service
public class ConcurrencySafeInventoryService {

    private final RedissonClient redissonClient;
    private final InventoryRepository inventoryRepository;

    public ConcurrencySafeInventoryService(RedissonClient redissonClient, 
                                           InventoryRepository inventoryRepository) {
        this.redissonClient = redissonClient;
        this.inventoryRepository = inventoryRepository;
    }

    public boolean reserveStock(String skuCode, int quantity) {
        String lockKey = "lock:inventory:" + skuCode;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // Wait up to 5s to acquire; lease for max 10s
            boolean acquired = lock.tryLock(5, 10, TimeUnit.SECONDS);
            if (!acquired) {
                throw new IllegalStateException("Could not acquire lock for SKU: " + skuCode);
            }

            Inventory inventory = inventoryRepository.findBySkuCode(skuCode)
                    .orElseThrow(() -> new IllegalArgumentException("SKU not found"));

            if (inventory.getQuantity() >= quantity) {
                inventory.setQuantity(inventory.getQuantity() - quantity);
                inventoryRepository.save(inventory);
                return true;
            }
            return false;

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}

12. Enterprise Security with Spring Security 6 & OAuth2 / JWT

12.1 Modern `SecurityFilterChain` Bean Configuration

Spring Security 6+ replaces old web security adapters with functional lambda configurations:

SecurityConfig.java (Stateless JWT Resource Server) 
package com.ecommerce.order.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
@EnableMethodSecurity // Enables @PreAuthorize("hasRole('ADMIN')")
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable()) // Stateless REST APIs do not require CSRF
            .sessionManagement(session -> 
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/v1/products/**").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(jwt -> {})); // Validates JWT tokens against Issuer

        return http.build();
    }
}

12.2 Propagating JWT Context via Feign

When `OrderService` calls `InventoryService`, forward the user's Bearer token using a Feign `RequestInterceptor`:

FeignAuthForwardInterceptor.java 
package com.ecommerce.order.config;

import feign.RequestInterceptor;
import feign.RequestTemplate;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken;

@Configuration
public class FeignAuthForwardInterceptor implements RequestInterceptor {

    @Override
    public void apply(RequestTemplate template) {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth instanceof JwtAuthenticationToken jwtAuth) {
            String tokenValue = jwtAuth.getToken().getTokenValue();
            template.header("Authorization", "Bearer " + tokenValue);
        }
    }
}
